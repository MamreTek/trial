# Mamre 应用工程约定

版本：1.2 · 2026-11-03

本机统一入口：`mamre-workspace/standards/README.md`。本机读取当前规则；项目快照用于独立携带及本机规则不可访问时的回退。

## 适用范围与优先级

第 0 节的当前产品雏形约定适用于 MamreTek 所有产品；其余工程默认值适用于后续新建的 Web 应用，以及已明确要求迁移的 Pylon 前端。它是可复用的工程规则模板，不是已经生成并验证过的完整应用脚手架。

用户已确认：新 Web 应用前端使用 React 和 Ant Design（`antd`）。其余内容为工程默认值，具体项目可以记录有理由的差异。Pylon 的特定选择从研发规则索引读取。

执行优先级：用户当前明确指令 > 项目中明确记录的决定 > 本文默认值。普通实现细节按默认值推进，只询问会改变业务行为、交付范围、成本或兼容性的缺失信息。其他既有应用继续按各自约定维护，框架迁移需要明确的项目范围。

## 0. 当前产品雏形阶段

这是用户于 2026-11-03 确认的阶段性开发约定，适用于所有产品的雏形工作；不代表产品开发已经启动，也不恢复已停止的产品。

- 产品尚无可用真实后端时，先用 React + TypeScript + Ant Design React（`antd`）落地可交互雏形，验证核心业务流程、列表、表单、详情和状态变化。后端技术栈默认值不要求本阶段搭建服务、数据库或部署基础设施。
- 交互需要后台接口而接口尚未实现时，使用 Mock 数据和接口处理器。已有可用接口继续按其契约使用；隔离 Mock 与真实数据来源，不为演示替换既有后端、调用生产写接口或使用真实敏感数据。
- 先定义可供后端直接适配的 API 契约：方法与路径、请求与响应类型、字段含义及约束、标识符、分页/筛选/排序、状态变化、成功及错误结构。接口及其示例、前端类型、Mock 处理器保持一致；可以采用 TypeScript 契约或项目已有的 OpenAPI 等声明，不要求生成尚未开发的后端。
- 页面通过统一 API 客户端访问数据，Mock 与未来真实后端遵循同一契约；数据来源在适配层切换，避免将临时假数据散落在业务组件中。Mock 覆盖核心流程以及加载、空数据、校验失败和服务失败等可观察状态。产品形态确定后，真实后端按契约实现并用同一组请求/响应示例验证接入；不把契约草案当成接口已经实现。
- 本阶段暂不新增菜单权限、按钮权限、接口权限或相应权限管理配置，不将其作为新增雏形的验收门槛。导航、按钮及业务交互仍应正常实现。已有登录认证、RBAC、租户/资源隔离、权限检查及其验收契约保留，不删除、禁用或绕过，也不降低现有运行环境安全。
- 雏形页面或演示说明清楚标明“产品原型 / 模拟数据”及尚未具备的权限保护。隐藏入口、禁用按钮或 Mock 成功响应不构成授权控制，不能据此声称具备生产安全或生产就绪能力。未具备权限保护的雏形不接入生产数据，不部署到生产。
- 雏形验收验证交互、产品流程与 Mock/API 契约，将真实服务、数据持久化及新增权限列为后续适配项；已实现的真实能力按原契约验证。正式业务和安全验收仍使用真实后端。本阶段规则不授权删除已有能力、迁移既有框架或发布服务；与已有明确项目决定有实质差异时，记录影响及本期范围后处理。

## 1. 默认技术栈

| 层次 | 默认选择 | 使用边界 |
| --- | --- | --- |
| Web 前端 | React + TypeScript strict + Vite | 使用函数组件与 Hooks；业务页面按功能拆分 |
| UI | Ant Design React（`antd`） | 新应用使用 React 版本；统一通过主题 tokens 定制 |
| 路由 | React Router | 路由与布局集中管理；已有登录和权限入口按项目契约保留，新增雏形权限按第 0 节暂缓 |
| 包管理 | npm + 单一 lockfile | CI 使用 `npm ci`；保留既有项目已选定的包管理器 |
| 后端 | Go + go-zero | 真实后端开发阶段的默认值；本阶段缺失接口先按第 0 节定义契约并 Mock |
| 数据访问 | GORM + MySQL | 数据库变更使用版本化迁移；现有数据的兼容性明确验收 |
| Redis | 按实际用途启用 | 缓存、协调或任务确有需求时使用，基础模板不强制增加依赖 |
| Python | 适合该任务时引入 | 例如 OCR、数据处理；记录与 Go 服务的接口和运行方式 |
| 部署 | Docker + Docker Compose | 单企业、单实例为起步部署方式；多租户和 Kubernetes 按项目需求设计 |

创建应用时核对官方兼容要求，选择相互兼容的稳定版本，并在版本文件、依赖锁和 CI 中固定。模板维护规则，不把初始化时的“最新版”当作所有项目的长期版本。

## 2. 代码与依赖边界

- 前端默认按 `src/app`、`src/features/<feature>`、`src/shared` 组织；已有目录通过有范围的迁移逐步调整。
- 路由和布局放在 app 层；页面、接口调用和业务状态按功能归属。共享组件只抽取已出现的共同需求。
- API 请求经过统一客户端，集中处理超时、认证失效、错误展示和请求标识。
- 后端沿用项目已有 handler、logic/service、model 的分层。业务判断放在服务端，数据库访问与 HTTP 处理保持可测试的边界。
- 模板只沉淀通用工程能力；Pylon 的主机、SSH、监控和发布业务模块按新产品需求选择复用。
- 新依赖应有明确用途；优先使用已采用库的能力。新增基础设施和独立服务要说明实际收益及运行成本。

## 3. 界面与交互

- 使用 Ant Design 的主题、表单、表格、反馈、弹窗和抽屉能力，统一间距、状态和操作位置。
- 产品默认中文；代码标识符用英文。显示语言、时区和国际化范围属于项目配置，只有实现并验证后才能声称支持。
- 页面包含加载、空数据、失败和提交中状态；已有权限能力覆盖权限不足状态，新增雏形权限按第 0 节暂缓。提交中的操作防止重复触发。
- 列表明确搜索、筛选、排序和分页的行为；表单提供字段级校验和可操作的错误信息。
- 删除、停机、覆盖配置等有实际影响的操作清楚展示目标和影响。结果以服务端返回为准。
- 兼顾桌面与手机浏览；关键操作可通过键盘完成，状态不能只依靠颜色表达。

## 4. API 与数据约定

- 默认使用版本化 REST/JSON。新应用从 `/api/v1` 起步；Pylon 保留现有 `/api/pylon/v1` 契约，另有迁移需求时再变更。
- 新接口约定统一的成功、分页和错误结构；HTTP 状态与错误含义一致，错误包含可定位的请求标识。既有接口的返回结构在兼容范围内维护。
- 采用 go-zero 的真实后端以 API 声明作为生成代码的来源。修改接口时同步声明、生成结果、前端类型及相关文档；尚无后端的雏形先按第 0 节维护契约及 Mock。
- 真实服务端验证参数、资源归属、状态转换和权限；浏览器传来的角色、租户或资源标识不能代替授权。Mock 不提供这些安全保证，现阶段新增权限按第 0 节暂缓，既有权限检查保留。
- 时间在服务端统一记录为 UTC，接口使用带时区的标准表示，页面按选定时区展示。
- 涉及金额时使用最小货币单位整数或明确精度的 decimal，并记录币种；避免浮点金额计算。
- 表结构变更提供有序迁移及升级说明，明确数据保护和失败恢复方式。演示数据与正式初始化分开。
- 长时间执行的业务任务提供持久状态、有限超时和可查询结果。重试依据操作是否可安全重复设计。

## 5. 认证、权限与可追溯性

- 接入真实后端的新 Web 应用优先采用服务端可验证、可撤销的登录会话；采用 cookie 时配套 HttpOnly、Secure、SameSite 和 CSRF 防护。既有项目迁移前保留已约定的认证契约。
- 真实应用的权限在后端执行，前端按权限展示入口；现阶段新增雏形的菜单、按钮、接口权限按第 0 节暂缓，不据此移除已有角色权限、关键操作记录或其他安全控制。
- 密钥、密码和云凭据保存在服务端受控配置或密钥存储中；日志和回读接口展示必要的脱敏信息。
- 执行 SSH 的产品验证主机身份；远程执行有超时、输出限制和明确的成功/失败状态。这些规则按功能适用，不要求普通业务应用实现 SSH 能力。
- 实际部署、支付、对外沟通和生产变更仍按用户授权执行；工程模板不扩大执行权限。

## 6. 质量与验收

- Go 变更按范围检查格式、`go vet`、`go test` 和构建；前端提供 lint、typecheck、test 和 build 入口。
- 前端默认使用 Vitest 与 React Testing Library 测试行为；关键完整流程按需要用 Playwright 验证。测试围绕本期业务结果、已实现的权限、数据一致性和失败恢复设计；雏形中明确延期的真实后端与新增权限不冒充已验收能力。
- 纯文档等低影响改动核对内容、路径和格式；运行脚本或配置生成逻辑有变更时，验证实际生成行为与幂等性。
- CI 重现必要的本地检查。验收说明写清已验证内容、失败项和环境限制。
- Mock 用于缺失后端产品的雏形开发、雏形验收与隔离测试，并记录覆盖的 API 契约和数据来源。正式功能验收使用真实接口和可恢复的测试数据，雏形验收通过不代表真实业务、权限或生产安全验收通过。

## 7. 部署与维护

- 提供不含真实密钥的配置示例、启动说明、存活与就绪检查、日志定位方法及必要的持久卷。
- 升级涉及数据库时，说明备份、迁移、兼容性和恢复方式；备份能力的验收包含恢复验证。
- 构建结果和部署配置可追溯到版本。部署权限、服务承诺和生产发布方式按项目约定。

## 8. 需求与 Git 流程

- 需求文档放在源仓库外、该项目有效工作流记录指定的位置。本机记录位于 `~/.codex/mamre/projects/<repository-name>.toml`；按 origin 校验项目、Issue provider 和需求路径，不因缺少项目本地 `.codex` 重复接入。
- 按已安装的 `product`、`dev` 流程执行；产品需求、实现范围和可观察的验收标准关联到同一项工作。
- 使用 Issue 分支和 pull request 交付；保留无关改动，避免直接提交或推送到受保护的主分支。
- Issue、PR 和其他 provider-facing 内容使用英文。本地需求文档使用项目要求的语言。
- 按影响运行检查并记录结果。评审依项目要求进行；合并和生产发布遵循用户已给出的授权。
- 一个需求聚焦一个可交付结果。发现额外问题时记录其影响，独立安排范围，避免顺带重写。

## 9. 新应用只需补充的信息

默认约定可自动沿用。每个项目只需确定或从现有资料中解析：

1. 项目名称、代码仓库及需求记录位置。
2. 首批用户、核心问题和第一条完整业务流程。
3. 关键业务实体、验收标准与本期范围。
4. 部署目标、外部系统和数据隔离要求中与默认值不同的部分。

只有偏离默认值的决定需要额外说明原因及影响。单个项目的例外不自动成为其他应用的规则。

## 10. 项目差异

- Pylon 约定从研发规则索引的项目条目读取，不作为其他应用的业务要求。
- 项目只记录与默认值不同的决定。通用规范集中维护，更新规范或初始化完成不代表业务代码已经实现。
